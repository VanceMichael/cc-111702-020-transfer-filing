# 业务运行边界
当前可查询：联合持有人名单与份额、各自确认依据、代表、门户草稿的可操作权限、门户受理状态与补正记录。
当前写入操作：分单位收集确认、更正联系人、确定或更换代表、回读并汇总门户草稿、按门户补正。

## 原始依据
来源请求保存方法、路径、状态、字节数与响应摘要，不保存授权原文。拒绝或不完整响应不能作为领域收件成功；业务结果和请求收据分别可查。进程内的写入序列只保证本进程存储互斥，不代表来源具备幂等或多进程协调能力。

## 领域决定
- 确认职责核对的是**确认当时看过的持有人名单、份额安排和该持有人自己的资料版本**，而不是一个“已确认”布尔值。份额或参与方变化使所有相关确认失效；某家资料修订变化只使该家确认失效。
- 联系人更正是可单独办理的事项，不改变参与方、份额或资料版本，因此不使确认失效。
- 代表只负责汇总和提交，不能替其他持有人作出确认；代表可以汇总其他持有人已有的确认记录，但不能代替其生成新的确认。
- 更换代表只改变办理权限。已确认的依据、资料归属和退出单位的资料都保留在原持有人名下，不因换代表被重新收集或划归新代表。
- 换代表后，已上传草稿及附件在门户里的可继续权限以门户实际回读（`canOperate`、`ownerApplication`、`attachments`、`acceptedReceipt`）为准，本地登记不能替代回读。
- 门户已经受理的申请只能按门户允许的补正办理；本地不重新开一张相同申请来隐藏旧受理。回读暂时看不到受理号时保留原受理依据，不按新草稿重新报送。
- 尚未受理时继续收齐有效材料；明显失效的确认回到相应单位的待办，并说明不能提交的原因（`pending[].reason`）。
- 某家确认被来源明确拒绝（400/409/422）时只让该家回到待办；连接失败或来源故障仍整体回滚，不提交半成品状态。

## 追溯
每个业务申请可从 `GET /state` 或 `POST /collect` 的结果追到：
`confirmations[]`（各家确认依据与当前是否有效）、`pending[]`（不能提交的单位与原因）、`exited[]`（退出单位及其资料）、`representative` 与 `representativeHistory`、`drafts[]`（当前代表实际可操作的草稿、附件归属与回读历史）、`submissions[]` 与 `corrections[]`（受理号与补正记录）。

这些拒绝属于当前正常办理契约，不代表来源失败可视为业务成功。各决定在状态提交前完成，拒绝不会消耗本地办理状态。
